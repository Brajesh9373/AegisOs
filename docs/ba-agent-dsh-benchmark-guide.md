# BA Agent Benchmark: Native AegisOS vs DeepSeek Harness

## Status

The AegisOS Business Analyst profile is configured as a real DeepSeek Harness (DSH) package profile and targets `glm-5` through an Anthropic Messages-compatible gateway. The native BA client is configured for the same gateway and model. The DSH route is not a Python substitute: the benchmark reaches the pinned DSH CLI, DSH profile composition, and DSH's `llm-pi-ai` provider path.

A successful DSH-to-GLM-5 smoke call has been completed through the repository-pinned executable. The benchmark remains a live integration workload: results depend on the gateway, model behavior, and local service availability when it is run.

## Security note

A credential was previously present in this document. It has been removed. Treat it as exposed: revoke or rotate it at the gateway, then use the replacement only through ignored local environment files or process environment variables. Never commit a credential, include it in a benchmark report, or paste it into a DSH profile.

## Architecture

```text
Native BA workflow
  backend/ecms/agent/ba/agent.py
  → Anthropic Messages-compatible GLM-5 gateway

DSH BA workflow
  backend/ecms/agent/dsh_runtime.py
  → packages/dsh-integration/node_modules/.bin/dsh (pinned)
  → business-analyst DSH package profile
  → @deepseek-ai/dsh-llm-pi-ai / glm-gateway
  → Anthropic Messages-compatible GLM-5 gateway
```

The DSH profile lives in `packages/dsh-integration/profiles/business-analyst/`:

- `package.json` declares `@deepseek-ai/dsh-base` and `@deepseek-ai/dsh-headless`.
- `cordis.patch.yml` provides an `anthropic-messages` `glm-gateway` route and selects `glm-5` as the DSH default.
- `pnpm-workspace.yaml` describes the profile package layout.
- `cordis.yml` and `$DSH_HOME/profiles/node_modules` are generated by DSH and must not be authored or checked in.

## Prerequisites

1. Install the pinned DSH integration dependency from the repository:

   ```bash
   cd packages/dsh-integration
   pnpm install --frozen-lockfile
   ./node_modules/.bin/dsh --version
   # Expected: 0.1.1-rc.2
   ```

2. Set gateway variables without placing secrets in source-controlled files:

   ```bash
   export ANTHROPIC_BASE_URL="https://your-anthropic-compatible-gateway"
   export ANTHROPIC_AUTH_TOKEN="<gateway-bearer-token>"
   export CLAUDE_CODE_SESSION_ID="<non-empty-session-id>"
   export LLM_MODEL="glm-5"
   ```

   `DSHRuntime` generates a UUID if `CLAUDE_CODE_SESSION_ID` is unset or blank. The gateway still requires a non-empty value on every request.

3. Install the backend project dependencies in the intended Python environment. Do not globally install DSH and do not copy profile files by hand: `DSHRuntime` synchronizes the repository-owned profile before execution.

## Run the smoke test

From the repository root:

```bash
cd backend
PYTHONPATH=. ./venv/bin/python - <<'PY'
import asyncio
from ecms.agent.dsh_runtime import DSHRuntime

async def main():
    result = await DSHRuntime(profile="business-analyst", timeout=120).run_agent_task(
        "Reply with exactly: DSH GLM-5 smoke test passed. Do not use tools."
    )
    print(result.output)

asyncio.run(main())
PY
```

This proves the actual DSH CLI can compose the profile and use the configured gateway. It does not replace DSH with a direct HTTP client.

## Run the benchmark

```bash
cd backend
PYTHONPATH=. ./venv/bin/python tests/test_ba_benchmark.py
```

The executable benchmark covers three briefs and three comparable stages:

1. `understand`
2. `clarify`
3. `finalize`

For both paths, finalization receives the preceding clarification as discovery conversation context. DSH structured stages pass through the same `FinalizedRequirements` validator used by the native path. If a structured DSH response is invalid, the runtime makes one corrective retry through the same real DSH CLI/profile path; invalid JSON, Markdown-fenced JSON, or schema-invalid output after that retry is a failed DSH stage, not a raw-text success.

The report is written to the system temporary directory (normally `/tmp/aegisos-ba-benchmark/benchmark_results.json`), so live benchmark output does not dirty the source tree. It records stage errors and counts success rates over stages actually attempted. A dependent stage is not fabricated after an earlier failure.

## Interpreting latency

The benchmark deliberately reports end-to-end wall-clock time, not model-only latency:

- **Native:** retrieval plus in-process BA orchestration and gateway/model execution.
- **DSH:** profile synchronization, DSH CLI process launch, DSH profile/plugin work, and gateway/model execution.

Compare the figures as operational-path latency. Do not attribute the difference solely to model performance or gateway variance. If model-only latency is required, capture timing at the gateway with an approved observability mechanism rather than infer it from this benchmark.
