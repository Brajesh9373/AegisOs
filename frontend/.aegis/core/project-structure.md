# AegisAI Project Structure

This document defines the definitive, permanent repository structure specification for AegisAI. It establishes the physical boundaries that enforce the logical architecture, ensuring the codebase remains modular, scalable, and strictly governed.

## 1. Repository Philosophy
The repository structure is a physical manifestation of the AegisAI architecture. Folder boundaries equal module boundaries. Predictability, strict isolation, and discoverability are paramount.

## 2. Monorepo Structure
AegisAI utilizes a monorepo approach. All applications, core packages, documentation, and infrastructure scripts reside in a single repository. This ensures atomic commits across boundaries and unified versioning.

## 3. Root Directory Responsibilities
The root directory serves purely as the entry point and configuration hub for the monorepo tooling. It contains only top-level organizational folders (`apps`, `packages`, `docs`, etc.) and root configuration files (e.g., `.gitignore`, monorepo management configs).

## 4. apps Structure
The `apps/` directory contains deployable, entry-point applications. These are the executing environments that wire together underlying packages. 
* Contains: `web/`, `api/`, `worker/`.

## 5. packages Structure
The `packages/` directory contains isolated, reusable domain and utility libraries. Packages contain business logic, database models, and governance rules.
* Contains: `runtime/`, `guardian/`, `database/`, `shared/`, `sdk/`, `ui/`, `events/`, `notifications/`.

## 6. docker Structure
The `docker/` directory holds containerization logic, `Dockerfile` templates, and `docker-compose` configurations for local development and base images.

## 7. docs Structure
The `docs/` directory is for developer and operator documentation, deployment guides, API references, and release notes. (Note: Core architectural authority resides in `.aegis/`).

## 8. tests Structure
The `tests/` directory is reserved for cross-project integration and end-to-end (E2E) testing. Unit tests live directly alongside the code they test within `apps/` and `packages/`.

## 9. scripts Structure
The `scripts/` directory contains automation, build, CI/CD, and deployment utility scripts.

## 10. .aegis Structure
The `.aegis/` directory is the immutable source of truth, constitution, and architectural mandate for the project. It dictates what the platform is and how it must be built.

## 11. Module Boundaries
A folder within `packages/` or `apps/` is a hard module boundary. A module must export a strict public interface. Internal files of a module must never be imported directly by another module.

## 12. Shared Code Rules
Code used by more than one package or app must be extracted into the `packages/shared/` module or a specific domain package. Duplication is forbidden.

## 13. Dependency Rules
Dependencies must flow strictly downward. `apps/` depend on `packages/`. `packages/` depend on other `packages/` or external libraries. `packages/` must never depend on `apps/`.

## 14. Import Rules
Imports must use path aliases or package names (e.g., `@aegis/guardian`) rather than relative deep-linking (e.g., `../../../packages/guardian/src/index`).

## 15. Folder Naming Standards
All folders must use `kebab-case`. Names must clearly indicate the domain or technical purpose.

## 16. File Naming Standards
All files must use `kebab-case.ext`, except for files exporting a single class or UI component, which use `PascalCase.ext`.

## 17. Package Naming Standards
Packages must be named using a consistent scope prefix (e.g., `@aegis/[package-name]`).

## 18. Asset Organization
Static assets (images, fonts) belong in `apps/web/public/` or an equivalent static directory, never mixed with business logic.

## 19. Configuration File Organization
Module-specific configurations live within their respective module root. Global configurations live at the monorepo root.

## 20. Environment File Rules
`.env` files contain secrets and environment-specific overrides. They must never be committed. `.env.example` templates must be maintained and committed.

## 21. Generated File Rules
Generated code (e.g., ORM clients, API SDKs) must output to designated `generated/` or `.cache/` directories and must be excluded from version control if reproducible.

## 22. Temporary File Rules
Temporary files must be written exclusively to the operating system's `tmp/` directory or a git-ignored `tmp/` at the root.

## 23. Build Artifact Rules
Build outputs (e.g., `dist/`, `build/`) must be entirely git-ignored and regenerated by the build pipeline.

## 24. Documentation Placement Rules
Code-level documentation (docstrings) lives in the source. Architectural decisions live in `.aegis/19-decisions/`. Operational guides live in `docs/`.

## 25. Testing Folder Standards
* Unit tests: `__tests__/` alongside the source files.
* Integration/E2E: `tests/integration/` or `tests/e2e/` at the root.

## 26. Package Responsibilities
Packages are headless, domain-specific logic blocks. They do not know how they are hosted or deployed.

## 27. Application Responsibilities
Applications (in `apps/`) are orchestrators. They initialize configurations, set up dependency injection, and expose the packages via HTTP/UI/Message Queues.

## 28. Cross Module Communication Rules
Cross-module communication must happen via exported interfaces, APIs, or the `events` package. Direct database-level joins across bounded contexts are heavily restricted.

## 29. Circular Dependency Prevention
A module cannot import a module that imports it back. Extract shared interfaces to a neutral package to resolve cyclic dependencies.

## 30. Future Expansion Strategy
New features fall into three categories:
1. New endpoint/UI for existing feature -> update `apps/`.
2. New core capability -> new package in `packages/`.
3. New operational script -> update `scripts/`.

## 31. Directory Ownership Rules
Code owners (teams or individuals) must be explicitly mapped to top-level directories in a `CODEOWNERS` file.

## 32. Forbidden Structure Patterns
No "god folders" (e.g., a massive `utils/` folder with unrelated logic). No shadow architectures (building sub-apps inside packages).

## Recommended Directory Tree

```
.aegis/                  # Absolute architectural truth
  ├── 00-constitution/
  ├── core/
  ├── agents/
  └── modules/
apps/                    # Deployable boundaries
  ├── web/               # UI and React/Frontend logic
  ├── api/               # API endpoints, routing, controllers
  └── worker/            # Background job processors
packages/                # Core domain and logic
  ├── database/          # Database connections, models, migrations
  ├── events/            # Event bus, messaging contracts
  ├── guardian/          # Security, governance, RBAC enforcement
  ├── notifications/     # Email, SMS, in-app routing
  ├── runtime/           # AI execution, prompt construction
  ├── sdk/               # External programmatic access
  ├── shared/            # Common utilities, constants, types
  └── ui/                # Reusable design system components
docs/                    # Operational and developer guides
docker/                  # Container infrastructure
scripts/                 # Automation and CI/CD
tests/                   # Cross-project E2E and integration
```

### Module Placements
* **Future modules**: Must be created under `packages/`.
* **New packages**: Created as `packages/[new-domain]`.
* **Shared utilities**: Belong in `packages/shared/`.
* **Business logic**: Belongs in domain-specific `packages/`.
* **Runtime**: Belongs in `packages/runtime/`.
* **Guardian**: Belongs in `packages/guardian/`.
* **Database layer**: Belongs in `packages/database/`.
* **UI**: Belongs in `apps/web/` (app specific) and `packages/ui/` (shared).
* **Workers**: Belongs in `apps/worker/`.
* **SDK**: Belongs in `packages/sdk/`.
* **Integrations**: Belong in a new `packages/integrations/` or specific plugin package.
* **Future plugins/extensions**: Should live in a dedicated `packages/plugins/` directory.

## Never Do

* **Never** create random folders at the root.
* **Never** duplicate shared utilities across apps or packages.
* **Never** mix frontend presentation and backend server code in the same package.
* **Never** place business logic in UI components.
* **Never** place Runtime logic inside Guardian.
* **Never** place Guardian logic inside Runtime (they must remain completely decoupled).
* **Never** create circular package dependencies.

---

## Project Structure Constitution
Every contributor and AI assistant must permanently follow these structural rules:

1. **Root Integrity**: The root directory structure (`apps`, `packages`, `.aegis`, etc.) is immutable.
2. **Domain Isolation**: Packages must strictly encapsulate their domain; they cannot bleed into or directly manipulate another package's internal state.
3. **Execution Separation**: `apps/` orchestrate and deploy; `packages/` provide the logic. Do not mix these responsibilities.
4. **Architectural Supremacy**: If a structural decision conflicts with `.aegis/`, the structure must be corrected to match the documentation.
