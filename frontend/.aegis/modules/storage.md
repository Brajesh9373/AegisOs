# AegisAI Storage Architecture Specification

This document defines the definitive, permanent Storage Architecture for AegisAI. It establishes the physical and logical patterns for persisting all forms of data across the platform, from structured relational records to unstructured binary blobs, ensuring durability, encryption, and strict governance.

## 1. Storage Philosophy
Data is the enterprise's most valuable and volatile asset. The storage layer must treat all data as radioactive—it must be containerized, encrypted, access-controlled, and audited. AegisAI utilizes a Polyglot Persistence strategy: the type of data dictates the specific storage technology used, optimizing for read/write performance, cost, and compliance.

## 2. Storage Architecture
The architecture is cleanly separated into hot, warm, and cold tiers. Transactional metadata resides in a relational database. High-velocity ephemeral data lives in in-memory caches. Unstructured files and historical archives are relegated to highly durable Object Storage. All storage tiers are abstracted behind internal API facades; the core application logic never interfaces directly with storage drivers.

## 3. Structured Storage
PostgreSQL is the primary engine for all structured, relational data (Users, Roles, Tasks, Policies). It enforces referential integrity, Row-Level Security (RLS) for tenant isolation, and ACID guarantees for all transactions.

## 4. Object Storage
An S3-compatible object storage layer (e.g., AWS S3, MinIO) is used for all unstructured data. It provides practically infinite scalability for large binary payloads, document uploads, and backup artifacts.

## 5. File Storage
AegisAI actively avoids traditional networked file systems (NFS/EFS) to eliminate locking contention and statefulness in the application tier. All "files" are mapped to Object Storage.

## 6. Blob Storage
Used interchangeably with Object Storage to represent large, immutable binary chunks, such as compiled Plugin WebAssembly modules or encrypted license payloads.

## 7. Configuration Storage
System settings, feature flags, and UI configurations are stored as versioned JSON documents within PostgreSQL, benefiting from relational queries while maintaining schema flexibility.

## 8. Audit Storage
The Audit Ledger utilizes an append-only, hyper-optimized time-series datastore (or partitioned PostgreSQL tables) designed for high-velocity writes and complex compliance searches. Older audit logs are eventually flushed to WORM (Write-Once, Read-Many) Object Storage.

## 9. Memory Storage
Agent episodic and semantic memory is stored in a dedicated Vector Database (e.g., pgvector, Milvus). This allows for lightning-fast cosine similarity searches required for Retrieval-Augmented Generation (RAG).

## 10. Knowledge Storage
The raw source documents (PDFs, Word docs) are stored in Object Storage, while their mathematical representations (embeddings) are stored in the Vector Database. Both are strictly bound by the same RBAC identifiers.

## 11. Artifact Storage
Outputs generated by Agents (e.g., a synthesized CSV report, a generated image) are stored as distinct Artifacts in Object Storage, linked back to the originating Task ID in the relational database.

## 12. Encryption
All storage volumes (EBS, RDS) are encrypted at rest using AES-256. Object Storage buckets enforce Server-Side Encryption (SSE-KMS). Sensitive column data (API keys) is encrypted at the application level before being written to the database.

## 13. Compression
Large payloads (e.g., raw LLM context logs) are automatically compressed (e.g., gzip, zstd) by the application layer before being written to Object Storage to drastically reduce infrastructure costs.

## 14. Versioning
Object Storage buckets have versioning enabled by default. Overwriting a Knowledge document does not destroy the previous file; it simply creates a new version, allowing instant rollback.

## 15. Retention
Automated lifecycle policies enforce data destruction. For example, ephemeral Agent scratchpad files are physically deleted after 7 days; SOC2 audit logs are retained for 7 years.

## 16. Archiving
Data that is infrequently accessed (e.g., archived Workspaces) is automatically migrated to colder, cheaper storage tiers (e.g., S3 Glacier) to optimize costs without sacrificing availability.

## 17. Backup
All structured data undergoes continuous WAL archiving. Object storage relies on cross-region replication. (See Backup & Disaster Recovery Architecture for details).

## 18. Restore
Granular restoration (e.g., undeleting a specific Artifact) is supported via Object Storage versioning. Point-In-Time-Recovery (PITR) is used for catastrophic database failures.

## 19. Search
A dedicated Search Engine (e.g., Elasticsearch/OpenSearch) indexes metadata across all storage tiers, providing a unified, sub-second global search experience across Tasks, Knowledge, and Audit logs.

## 20. Scalability
The storage architecture scales horizontally. Read-replicas handle heavy reporting loads, and Object Storage scales infinitely by design.

## 21. Monitoring
Storage capacity, IOPS, and latency are continuously monitored. Alerts fire well before disk exhaustion (e.g., at 80% capacity) to allow automated or manual volume expansion.

## 22. Security
Every read or write request to any storage medium must pass through the API layer where the tenant's RBAC scope is validated. Direct database or bucket access by human operators is strictly prohibited in production.

## 23. Future Expansion
The architecture supports the integration of decentralized storage networks for cryptographic immutability of specific high-security audit trails.

## 24. Permanent Constraints
* All data at rest must be mathematically encrypted.
* Object Storage must be versioned.
* The Audit Ledger is append-only and immutable.
* Storage access perfectly mirrors Workspace/Organization ownership boundaries.
* Automated Backup and Recovery validation is mandatory.

---

## Never Do

* **Never** store sensitive data, API keys, or PII in plain text in the database.
* **Never** use a single, shared Object Storage bucket without strict prefix-based tenant isolation.
* **Never** allow the application tier to write to the local filesystem (except for `/tmp` during processing); containers must remain entirely stateless.
* **Never** execute heavy analytical queries (OLAP) directly against the primary transactional database (OLTP).

---

## Storage Constitution
The permanent Storage principles of AegisAI:
1. **The Principle of Isolation**: Data from Tenant A must never touch the physical or logical space of Tenant B without explicit, cryptographic permission.
2. **The Principle of Immutability**: What is written to the ledger cannot be unwritten. True enterprise accountability requires a permanent, unalterable memory.
3. **The Principle of Ephemerality**: If data does not need to be kept, it must be destroyed. Minimizing the data footprint inherently minimizes the attack surface.
