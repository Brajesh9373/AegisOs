# AegisAI Tool Execution Architecture Specification

This document defines the definitive, permanent Tool Execution Architecture for AegisAI. It establishes the mechanical lifecycle of how an AI Agent requests an action, how the system intercepts and validates that request, and how the physical execution is safely sandboxed and audited.

## 1. Tool Execution Philosophy
An LLM generating text is benign; an LLM executing a tool is a kinetic event. Tools cross the boundary from thought to action, directly manipulating enterprise data and external systems. Therefore, the Tool Execution pipeline must operate under the assumption that the LLM is attempting a hostile action. Trust nothing. Validate everything.

## 2. Objectives
The Tool Execution Architecture must:
* Intercept all tool call requests generated by the AI Provider.
* Mathematically prove the Agent has the necessary RBAC permissions to execute the tool.
* Subject the tool payload to Guardian's deep packet inspection.
* Execute the tool in an isolated environment that cannot compromise the core Runtime.

## 3. Execution Lifecycle
1. **Request**: The AI returns a JSON Tool Call.
2. **Resolution**: The system identifies the requested tool.
3. **Authorization**: RBAC validates the Agent's right to use the tool.
4. **Validation**: The JSON payload is validated against the tool's schema.
5. **Guardian Scan**: Guardian evaluates the payload against security policies.
6. **Execution**: The tool runs in a sandbox.
7. **Result Parsing**: The output is captured, sanitized, and returned to the AI.

## 4. Tool Resolution
The system maps the AI's requested function name (e.g., `github_create_pr`) to the internal Tool Registry. If the tool does not exist, the Execution engine returns a standardized `ToolNotFound` error to the LLM.

## 5. Tool Validation
The raw JSON arguments generated by the LLM are strictly validated against the tool's JSON Schema. Any extra parameters, missing required fields, or type mismatches cause an immediate failure (e.g., `ValidationError`).

## 6. Tool Authorization
Before execution, the system checks the active RBAC matrix. Does the human user who spawned this Agent have permission to run `github_create_pr`? Does the Agent itself have the `Developer` role? If either is false, execution is blocked.

## 7. Guardian Integration
The validated JSON payload is passed to Guardian. Guardian evaluates active policies (e.g., "Do not allow PRs to the `main` branch"). If Guardian blocks the request, an `ActionDenied` error is returned to the LLM with an explanation.

## 8. Runtime Integration
The Tool Execution Engine is a sub-component of the Task Engine. It operates synchronously, halting the LLM's generation loop until the physical tool execution completes and returns the result string.

## 9. Context Injection
Some tools require implicit context not provided by the LLM (e.g., a Jira tool needs the user's OAuth token, not the Agent's). The Execution engine securely injects these environment variables just-in-time, preventing the LLM from ever seeing the raw credentials.

## 10. Result Validation
The output of the tool (e.g., a massive JSON response from an API) is validated and often truncated. If a database query returns 1,000,000 rows, the Execution engine truncates it to 50 rows before returning it to the LLM to prevent context window explosion.

## 11. Retry Strategy
If a tool fails due to a transient network error (e.g., HTTP 502), the Execution engine implements an internal exponential backoff retry. The LLM is only notified if all retries are exhausted.

## 12. Timeout Strategy
Every tool execution has a strict, hardcoded timeout (e.g., 10 seconds). If a tool hangs, the Execution engine kills the thread and returns a `TimeoutError` to the LLM.

## 13. Sandboxing
Tools that execute arbitrary code (e.g., a Python Code Interpreter) are physically isolated. They run inside ephemeral, restricted Docker containers or WebAssembly (Wasm) runtimes that have no network access to the primary database or internal AegisAI microservices.

## 14. Monitoring
The latency, success rate, and error rate of every specific tool are continuously monitored. A spike in errors for the `Salesforce_Create_Lead` tool triggers an immediate operational alert.

## 15. Audit
Every tool execution is permanently written to the Audit Ledger. The record includes the raw requested JSON, the Guardian approval, the execution latency, and the exact result returned to the AI.

## 16. Security
Tools are treated as external, untrusted code. They are executed with the minimum privileges required (Principle of Least Privilege).

## 17. Error Handling
Errors returned to the LLM must be highly descriptive so the AI can self-correct. Example: Instead of "Error 400", return "ValidationError: The field 'date' must be in YYYY-MM-DD format."

## 18. Future Expansion
The architecture supports the integration of "Human-in-the-Loop (HITL) Execution," where specific high-risk tools automatically suspend the execution pipeline and ping a manager on Slack for an explicit "Approve" click before physically running.

## 19. Permanent Constraints
* Every single tool execution MUST pass through Guardian.
* Every single tool execution MUST be permanently auditable.
* Unauthorized tools or malformed payloads MUST NEVER execute.
* Tools MUST run in isolation; they cannot access AegisAI's internal memory or configuration directly.
* Tool execution MUST have strict timeouts.

---

## Never Do

* **Never** allow a tool to bypass the RBAC identity of the invoking User.
* **Never** pass raw API keys or database passwords into the LLM's context window; the Execution engine must manage secrets.
* **Never** execute code-generation tools (Python/Bash) on the same host machine running the core AegisAI Task Engine.
* **Never** swallow tool execution errors; the LLM must be explicitly told that its action failed so it doesn't hallucinate success.

---

## Tool Execution Constitution
The permanent Tool Execution principles of AegisAI:
1. **The Principle of Kinetic Control**: Talking is safe; acting is dangerous. The moment an AI asks to change the world, the system must freeze, verify the identity, check the rules, and only then pull the trigger.
2. **The Principle of Perfect Memory**: An AI may forget what it did yesterday, but the Enterprise must never forget. Every API call, database write, and email sent is etched into the permanent ledger.
3. **The Principle of the Blast Radius**: If a tool fails, crashes, or goes rogue, its destruction must be mathematically contained within a sandbox. The core OS must survive.
