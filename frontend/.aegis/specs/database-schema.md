# AegisAI Database Schema Specification

This document defines the complete logical database schema for AegisAI. It acts as the bridge between the high-level architecture and the physical SQL implementation.

## Database Philosophy
The database is the immutable source of truth. It must enforce absolute data integrity, strict multi-tenant isolation, and complete auditability at the schema level. Application logic may fail, but the database must never allow corrupted, orphaned, or unauthorized data to persist.

## Naming Standards
*   **Tables:** Plural, snake_case (e.g., `workspaces`, `task_executions`).
*   **Columns:** Singular, snake_case (e.g., `workspace_id`, `created_at`).
*   **Foreign Keys:** `[entity_singular]_id` (e.g., `user_id`).
*   **Junction Tables:** Alphabetical combination of joined tables (e.g., `role_user`).

## Primary Key Strategy
Every table utilizes a UUID (v4 or v7) as its primary key, named `id`. Auto-incrementing integers are strictly forbidden to prevent ID enumeration attacks and to facilitate distributed system synchronization.

## Foreign Key Strategy
Foreign keys must be explicitly defined at the database level with strict referential integrity. Constraints are mandatory.

## UUID Strategy
UUIDs are generated by the application layer before insertion to allow for offline creation and exact object tracking. The database enforces uniqueness.

## Soft Delete Strategy
Records are never physically deleted unless mandated by a specific GDPR/compliance purge. Every table includes a `deleted_at` timestamp. Queries must globally scope out soft-deleted records.

## Versioning Strategy
Highly mutable, critical configuration entities (Agents, Prompts, Knowledge) use a dual-table strategy: an active pointer table (`agents`) and an immutable append-only version table (`agent_versions`).

## Audit Strategy
The database triggers (or an application-level interception layer that cannot be bypassed) must record every `INSERT`, `UPDATE`, and `DELETE` operation to the `audit_logs` table, storing the exact JSON diff.

## Multi-Tenant Strategy
Row-Level Security (RLS) is the standard. Every table that belongs to a tenant must have an `organization_id` column. A missing `organization_id` on a tenant-scoped table is a schema failure.

## Entity Definitions

### 1. Workspace
*   **Purpose:** A secure boundary for isolated projects or environments.
*   **Ownership:** Belongs to an Organization.
*   **Relationships:** Has many Teams, Agents, Tasks.
*   **Lifecycle:** Created -> Active -> Archived -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** No.
*   **Audit Requirements:** Full audit on mutation.

### 2. Organization
*   **Purpose:** The root tenant entity representing a single company or customer.
*   **Ownership:** Platform level.
*   **Relationships:** Has many Departments, Workspaces, Users.
*   **Lifecycle:** Provisioned -> Active -> Suspended -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** No.
*   **Audit Requirements:** Strict audit on all changes.

### 3. Department
*   **Purpose:** A logical grouping within an Organization for budget and policy inheritance.
*   **Ownership:** Belongs to an Organization.
*   **Relationships:** Has many Teams.
*   **Lifecycle:** Created -> Active -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** No.
*   **Audit Requirements:** Full audit on mutation.

### 4. Team
*   **Purpose:** A group of Users within a Department or Workspace.
*   **Ownership:** Belongs to a Department.
*   **Relationships:** Has many Users (via junction), has many Workspaces (via junction).
*   **Lifecycle:** Created -> Active -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** No.
*   **Audit Requirements:** Full audit on membership changes.

### 5. User
*   **Purpose:** A human actor authenticated into the system.
*   **Ownership:** Belongs to an Organization.
*   **Relationships:** Has many Roles, belongs to many Teams.
*   **Lifecycle:** Invited -> Active -> Locked -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** No.
*   **Audit Requirements:** Full audit, specifically authentication events.

### 6. Role
*   **Purpose:** A named collection of Permissions (e.g., "Workspace Admin").
*   **Ownership:** Belongs to an Organization (Custom) or Platform (System).
*   **Relationships:** Has many Permissions, assigned to many Users.
*   **Lifecycle:** Created -> Active -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** No.
*   **Audit Requirements:** Full audit on mutation.

### 7. Permission
*   **Purpose:** A granular right to perform an action (e.g., `agent:execute`).
*   **Ownership:** Platform level (Immutable).
*   **Relationships:** Belongs to many Roles.
*   **Lifecycle:** Static.
*   **Soft Delete:** No.
*   **Versioning:** No.
*   **Audit Requirements:** None (static data).

### 8. Role Permission (Junction)
*   **Purpose:** Maps Roles to Permissions.
*   **Ownership:** Bound to Role.
*   **Relationships:** Links `roles` and `permissions`.
*   **Lifecycle:** Created -> Deleted (Hard Delete allowed for junction).
*   **Soft Delete:** No.

### 9. User Permission (Junction/Override)
*   **Purpose:** Explicit, direct permission overrides for a specific user.
*   **Ownership:** Bound to User.
*   **Relationships:** Links `users` and `permissions`.
*   **Lifecycle:** Created -> Deleted (Hard Delete allowed).
*   **Soft Delete:** No.

### 10. Agent
*   **Purpose:** The pointer to the active definition of an AI persona.
*   **Ownership:** Belongs to a Workspace.
*   **Relationships:** Has many Agent Versions, owns Agent Memory.
*   **Lifecycle:** Draft -> Active -> Deprecated -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** Pointer to `active_version_id`.
*   **Audit Requirements:** Full audit on pointer change.

### 11. Agent Version
*   **Purpose:** An immutable snapshot of an Agent's configuration (prompts, tools, models) at a point in time.
*   **Ownership:** Belongs to an Agent.
*   **Relationships:** Belongs to Agent.
*   **Lifecycle:** Created (Immutable).
*   **Soft Delete:** No.
*   **Versioning:** Is the version.
*   **Audit Requirements:** Creation audited.

### 12. Agent Owner (Junction)
*   **Purpose:** Maps human Users who have managerial rights over an Agent.
*   **Ownership:** Bound to Agent.
*   **Relationships:** Links `agents` and `users`.
*   **Lifecycle:** Created -> Deleted.
*   **Soft Delete:** No.

### 13. Agent Hierarchy
*   **Purpose:** Defines parent-child relationships for multi-agent swarms.
*   **Ownership:** Belongs to a Workspace.
*   **Relationships:** Links `parent_agent_id` to `child_agent_id`.
*   **Lifecycle:** Created -> Deleted.
*   **Soft Delete:** No.

### 14. Agent Memory
*   **Purpose:** Stores long-term episodic memory for an Agent.
*   **Ownership:** Belongs to an Agent.
*   **Relationships:** Belongs to Agent.
*   **Lifecycle:** Created -> Pruned.
*   **Soft Delete:** Hard Delete upon pruning or Agent deletion.
*   **Versioning:** No.
*   **Audit Requirements:** None (high volume).

### 15. Knowledge
*   **Purpose:** A logical document or dataset uploaded for RAG.
*   **Ownership:** Belongs to a Workspace.
*   **Relationships:** Has many Knowledge Versions.
*   **Lifecycle:** Uploaded -> Processing -> Active -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** Pointer to `active_version_id`.
*   **Audit Requirements:** Full audit on metadata changes.

### 16. Knowledge Version
*   **Purpose:** An immutable binary snapshot and metadata of a Knowledge document.
*   **Ownership:** Belongs to Knowledge.
*   **Relationships:** Belongs to Knowledge.
*   **Lifecycle:** Created (Immutable).
*   **Soft Delete:** No (but storage backend may archive).
*   **Versioning:** Is the version.
*   **Audit Requirements:** Creation audited.

### 17. Skill
*   **Purpose:** An external integration or capability available to Agents.
*   **Ownership:** Organization or Platform.
*   **Relationships:** Has many Skill Versions.
*   **Lifecycle:** Registered -> Active -> Disabled -> Soft Deleted.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** Pointer to `active_version_id`.
*   **Audit Requirements:** Full audit.

### 18. Skill Version
*   **Purpose:** An immutable snapshot of the API schema/configuration for a Skill.
*   **Ownership:** Belongs to Skill.
*   **Relationships:** Belongs to Skill.
*   **Lifecycle:** Created (Immutable).
*   **Soft Delete:** No.
*   **Versioning:** Is the version.
*   **Audit Requirements:** Creation audited.

### 19. Task
*   **Purpose:** A defined objective or request submitted by a User or Agent.
*   **Ownership:** Belongs to a Workspace, initiated by a User or Agent.
*   **Relationships:** Has many Task Executions.
*   **Lifecycle:** Queued -> Running -> Completed/Failed.
*   **Soft Delete:** No. Historical ledger.
*   **Versioning:** No.
*   **Audit Requirements:** Yes.

### 20. Task Execution
*   **Purpose:** The immutable log of an LLM's attempt to complete a Task.
*   **Ownership:** Belongs to a Task.
*   **Relationships:** Belongs to Task, Agent Version.
*   **Lifecycle:** Created -> Finalized.
*   **Soft Delete:** No.
*   **Versioning:** No.
*   **Audit Requirements:** Highly audited.

### 21. Workflow
*   **Purpose:** A DAG defining a multi-step process.
*   **Ownership:** Belongs to a Workspace or Department.
*   **Relationships:** Has many Workflow Steps (internal JSON).
*   **Lifecycle:** Draft -> Published -> Archived.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** Yes (similar to Agent Versioning).
*   **Audit Requirements:** Full audit.

### 22. Approval
*   **Purpose:** A suspension point requiring human intervention.
*   **Ownership:** Belongs to a Workspace, linked to a Task.
*   **Relationships:** Links to `TaskExecution` and `User` (Approver).
*   **Lifecycle:** Pending -> Approved/Rejected.
*   **Soft Delete:** No.
*   **Versioning:** No.
*   **Audit Requirements:** Strict audit.

### 23. Approval History
*   **Purpose:** Immutable log of who approved what, when, and with what comments.
*   **Ownership:** Belongs to an Approval.
*   **Relationships:** Belongs to Approval.
*   **Lifecycle:** Created (Immutable).
*   **Soft Delete:** No.
*   **Versioning:** No.
*   **Audit Requirements:** Strict audit.

### 24. Policy
*   **Purpose:** A Guardian rule defining acceptable behavior.
*   **Ownership:** Organization or Department.
*   **Relationships:** Applies to scopes (JSON matrix).
*   **Lifecycle:** Draft -> Active -> Disabled.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** Yes (similar to Agent Versioning).
*   **Audit Requirements:** Strict audit.

### 25. Prompt
*   **Purpose:** A reusable text template.
*   **Ownership:** Organization, Department, or Workspace.
*   **Relationships:** Has many Prompt Versions.
*   **Lifecycle:** Active -> Archived.
*   **Soft Delete:** Yes (`deleted_at`).
*   **Versioning:** Pointer to `active_version_id`.
*   **Audit Requirements:** Yes.

### 26. Prompt Version

### 27. AI Provider

*   **Ownership:** Platform or Organization.

## Entity Relationships & Cascade Rules
*   **`users` -> `organizations`**: Many-to-One. **RESTRICT**. You cannot delete an Organization if it has Users.
*   **`workspaces` -> `organizations`**: Many-to-One. **CASCADE** (Soft Delete). Archiving an Org archives the Workspace.
*   **`agents` -> `workspaces`**: Many-to-One. **CASCADE** (Soft Delete).
*   **`agent_versions` -> `agents`**: Many-to-One. **RESTRICT**. You cannot delete an Agent if versions exist (which is always). Agents must be soft-deleted.
*   **`task_executions` -> `tasks`**: Many-to-One. **CASCADE** (Hard Delete, usually reserved for compliance purges).

## Multi-Tenant Isolation
All tables below the `Organization` level MUST contain an `organization_id` foreign key. This facilitates PostgreSQL Row-Level Security (RLS) policies: `CREATE POLICY tenant_isolation ON workspaces USING (organization_id = current_setting('app.current_tenant_id')::uuid);`

## Database Schema Constitution
The permanent Schema principles of AegisAI:
1. **The Principle of Relational Integrity**: The database is not a dumb data store. It is the final enforcer of logic. If a relationship is required, a Foreign Key constraint must exist.
2. **The Principle of Soft Deletion**: Data is corporate memory. Unless legally mandated, we do not perform `DELETE` operations on core entities. We update `deleted_at`.
3. **The Principle of the Ledger**: Transactions happen, states change, but history is append-only. The Audit Log and Execution Logs are immutable, untruncatable ledgers.
